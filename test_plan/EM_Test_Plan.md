## 1. Purpose

Verify the EM Testing Window behaves correctly and safely across every meaningful user
path: normal operation, invalid actions, interruptions at every phase of a run, input
boundaries, and full end-to-end sessions. This is a safety-relevant module: it drives a
real actuator into a load cell and sensor, so the fault and interruption paths carry the
highest priority.

## 2. Scope

In scope: the EM Testing Window and its run lifecycle (Stories 1.5.1 - 1.5.11), including
hardware connection gating, the run state machine, the live graph, force-limit and spike
safety, disconnect handling, completion, analysis hand-off, and window close.

Out of scope here (covered by their own plans): Main Window setup, Test Configuration,
the Existing-Test / Redo flow, and the EM Analysis window internals. This plan references
them where an EM path depends on them.

## 3. How "every possible path" is made complete

We do not enumerate paths freehand. Each path category below is generated by a named
technique so the coverage is finite and auditable:

| Category | Technique | What it covers |
|---|---|---|
| Functional (F) | Acceptance-criteria verification | Each story's happy path and stated behavior |
| Negative (N) | State-transition (illegal actions) | Every action taken in a state where it should be blocked or ignored |
| Interruption (I) | Phase x interrupt matrix | Pause / Close / disconnect at every phase of a run |
| Boundary (B) | Boundary value analysis | Run-count edges that change EM behavior |
| Journey (J) | End-to-end scenarios | Realistic multi-step sessions that chain features and expose state leakage |

## 4. Run phases (used by the Interruption matrix)

A single EM run passes through these phases. The interruption cases (EM-I-xx) cross each
phase with each available interrupt.

- **P1** Home to the 17 mm baseline
- **P2** Gap approach toward the sensor
- **P3** Press / descend until the force target
- **P4** Retract to the start position
- **P5** Between-runs pause (multi-run only)

Available interrupts in the EM window: **PAUSE**, **Close window**, **Zaber unplug**,
**FUTEK unplug**. (The EM window has no separate Stop button; closing is the stop path.)

## 5. Legends

**Priority** - Safety-critical: a failure can damage hardware or the sensor (force limits,
spikes, disconnects, motion during interrupts). Core: primary functionality. Minor:
cosmetic or convenience.

**Environment** - Sim: runs with no hardware (Mac / simulated). Rig: requires Windows +
Zaber + FUTEK. Both: run in sim first, confirm on the rig.

**Status** (filled during execution) - Not Run / Pass / Fail / Blocked.

## 6. Open decisions to resolve before execution

- **Force target and ceiling values.** The user stories state a 20 N EM press target and a
  28 N hard ceiling; the current code uses 32 N (UPPER_LIMIT_N) and 33 N
  (FORCE_CEILING_N). Cases EM-F-10, EM-I-02, and others depend on the agreed value. Settle
  this with the team before running the force-limit cases, and update the Expected Result.

## 7. Execution notes

- Run all Sim cases first; they are fast and repeatable and catch most logic and validation
  defects before hardware time is spent.
- Rig cases, especially the Safety-critical fault and interruption cases, require
  deliberately causing the fault (unplugging a cable, pressing into metal). They only count
  when the fault is actually injected.
- Log each failure as a defect with its Test Case ID in the Defect / Notes column and re-run
  the case after the fix (regression).
